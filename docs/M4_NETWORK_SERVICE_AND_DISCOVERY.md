# M4.4–M4.7: Windows network service, scoped game discovery and launch integration

2026-11-27. Development candidate. Not a Windows game certification or production installer.

## Privilege separation

- The existing Go agent binary has a Windows SCM service mode and a normal
  pipe-client mode. The Windows Tauri process invokes only the pipe client;
  Linux/macOS development retains the original private stdin agent.
- Administrator-owned installation policy fixes the HTTPS platform origin,
  Ed25519 issuer public key and a specific Windows user SID. The service
  verifies that SID resolves to a user. go-winio uses local-only named pipes;
  the DACL denies network logons, allows SYSTEM/administrators and only the
  selected user with narrowly scoped data/attribute rights (no create-instance
  right). The client verifies the pipe server PID against the registered
  running SCM service before sending the login token.
- The service checks the user ID against the authenticated platform session
  before using a per-account private state directory. It independently enrolls
  keys and validates the signed, nonce/session-bound room snapshots. No
  caller-supplied executable, CA, state path, route, shell command or issuer
  replacement is accepted. One native room overlay per installed service,
  with one bounded JSON request per session. Disconnect/extra input, blocked
  status writes or service stop cancel the session. Private keys stay in the
  protected service directory.
- Service runs as LocalSystem because Wintun/route administration is required.
  This is a narrower boundary than elevating the entire renderer, not a
  completed security review or Windows least-privilege audit. Game execution
  remains normal-user only. The driver is not bundled. The explicit
  administrator first-install script verifies both file hashes, verifies the
  Wintun Authenticode signature, creates a restricted Program Files root,
  installs a fixed SCM service and starts it. Uninstall stops/removes the
  service and preserves identity data. No automatic update or silent overwrite.

See [Windows network-service kit](../deploy/windows/README.md). Build using
`bash scripts/build-windows-network-kit.sh`; output under
`agent/bin/windows-network-kit` contains the x64 PE agent, SHA256SUMS and
install/uninstall documentation/scripts. The complete Tauri installer is
not generated by this kit.

## Controlled discovery policy

The authority optionally enables `BATTLE_NETWORK_GAME_DISCOVERY=true`
(default false), signing the immutable room game ID and a fixed local
adapter profile in each network snapshot. Only Warcraft III currently
selects `warcraft3-directed-v1`: room /24 directed broadcast, UDP port 6112.
The agent derives the one allowed destination from the signed local address.
It never accepts arbitrary forwarding destinations or ports from the server.
The profile is a candidate for classic LAN discovery, based on publicly
documented implementations such as
https://github.com/Qyperion/WC3LanGame; it is not a certified game version.

Linux uses existing Network Core EX discovery codec/guard. Windows candidate
uses Wintun with the room's connected /24 only in this mode; preflight rejects
overlapping non-default routes throughout the subnet. WireGuard exact peer
authorization, guard and allowlisted UDP codec remain in place. Windows does
not redirect limited broadcast, multicast, physical LAN, IPX or arbitrary
Ethernet. Windows native delivery/interface selection still needs validation.
macOS stays unicast-only. Unsupported game or disabled policy does not add
the discovery route. The client shows actual sent/received/dropped counters.
Unchanged discovery policy can survive a transport-only lease/node refresh.

In shared MongoDB authority mode all instances must use the same discovery
setting. Disabled setting preserves the existing configuration fingerprint;
enabling on an existing shared database requires a coordinated configuration
migration (not implemented; do not edit the fingerprint by hand). Use a fresh
isolated development database for enabled shared-mode experimentation.

The shared engine is pinned to candidate
`752e549feb94afa17755a65daf09cc89bd9235cb`, branch
`codex/nc-m4-windows-discovery`; no local Go replace or stable SDK release.

## Game adapters

- Warcraft III: experimental directed UDP discovery profile, not proof that
  a particular game build sends/receives it or chooses Wintun correctly.
- CS 1.6: optional Launch and join in the matching room's game library.
  User selects a current native agent-reported room peer and a game port
  (27015 initial value). The Rust command resolves the peer from the current
  authenticated network status, validates room/game/expiry/subnet, displays
  the target in native confirmation and revalidates after confirmation.
  Only the fixed local GoldSrc +connect address argument is appended, never
  an arbitrary command. The peer must already be running a compatible
  server; process launch does not prove game connection.
- Red Alert 2/Yuri's Revenge: original LAN protocol is IPX; the installed
  edition/network components need separate compatibility validation (see
  https://www.pcgamingwiki.com/wiki/Command_%26_Conquer%3A_Red_Alert_2).
  IPv4 broadcast or Wintun cannot be presented as native IPX compatibility.
  No third-party game patch, replacement DLL or license bypass is installed.
- Custom LAN: user-selected executable and manual authorized peer IPv4.

## Verification and remaining gates

The initial isolated Tokyo Linux network test
`python3 scripts/test-room-network.py --ice --multi --refresh --discovery`
passed. Four independent network namespaces and two TLS relays exchanged
actual ICMP/TCP/UDP. A room's directed UDP 6112 payload reached both a
direct-ICE peer and a relay peer; the other port and the separate room did
not receive it. Relay failover retained virtual interfaces, lease renewal
retained the TCP connection, and member departure / authority loss
revoked routes. These are synthetic socket tests, not commercial game tests.

Go IPC policy/EOF/unauthorized-origin unit tests and race checks, shared
core Go tests/vet, Windows x64 Go cross-build and PE generation, isolated
Rust game/network unit tests (3 including current-room CS target validation
and fixed join arguments) and Windows target compile check passed.
Java Maven package and Vue production build passed.

All available remote hosts are Linux. No actual Windows service startup,
named-pipe ACL/PID acceptance, Wintun driver load, native route/broadcast
delivery, PowerShell installer execution, Windows desktop bundle or
commercial game session has been verified. No unrestricted Windows L2/TAP
or IPX compatibility implementation, no driver redistribution, no release.

Final pinned-candidate build: Go module resolves the published core commit
without a local replace; Go race tests and vet passed, Windows x64
development kit was generated as a PE32+ executable and its SHA256SUMS
verified. The dual-browser UI regression passed, including game-library
navigation and disabled native launch controls in the browser.
